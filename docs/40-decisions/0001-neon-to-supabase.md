# ADR 0001 — DB를 Neon에서 Supabase로 옮긴 이유

- 상태: 채택됨
- 날짜: 2026-07 (이관 완료)
- 관련 문서: [README 배포 항목](../../README.md), [아키텍처 가이드](../00-overview/02-architecture.md)

## 배경

Render 무료 웹 서비스는 15분 무활동 시 슬립하고, 콜드 스타트에 수십 초가 걸린다.
이를 막으려고 외부 크론(cron-job.org)으로 주기적 핑을 걸어 두었다.

당시 DB는 Neon 무료 티어였다. "Neon이 5분 유휴 시 정지하니 `/`를 4분 간격으로 호출한다"는
규칙을 세웠고, **8일 만에 월 compute 쿼터(약 192h)를 전부 태우고 DB가 정지했다.**

## 무엇이 진짜 원인이었나

규칙의 인과가 틀렸다. 핑이 DB를 깨운 것이 아니다.

**앱이 살아 있는 동안 Prisma 엔진이 커넥션 풀을 계속 열어 두는 것**이 원인이었다.
Neon의 자동 정지 조건은 "활성 커넥션 0개"인데, Prisma가 그 조건을 영구히 막고 있었다.
즉 크론이 앱을 깨울 때마다 DB도 24시간 과금 상태로 끌려 들어갔다.

핑 간격을 늘리는 것으로는 해결되지 않는다. 앱이 깨어 있는 한 커넥션은 유지된다.

## 결정

DB를 **Supabase**(PostgreSQL + pgvector)로 옮긴다. Storage도 같은 프로젝트를 쓴다.

Supabase 무료 티어는 **compute 시간을 재지 않는다.** 커넥션이 계속 열려 있어도
같은 사고가 재현되지 않는다. 대신 다른 제약이 걸린다:

- DB 0.5GB, Storage 1GB
- 프로젝트가 **1주일 무활동 시 일시정지** — 장기 방치 주의

## 결과

- 크론은 유지한다. 단, `/`가 아니라 **`/item/list`**를 호출한다.
  `/`는 DB를 건드리지 않아 Supabase 무활동 타이머를 리셋한다는 보장이 없다.
  `/item/list`는 인증이 없으면서 실제로 DB를 조회하므로 활동 기록이 확실히 남는다.
- 간격은 10분(Render 슬립 기준 15분에 여유), 07:00–02:00 KST.
- Render 무료 인스턴스 시간(월 750h, 계정 합산) 중 약 590h를 쓴다.
  **무료 웹 서비스를 하나 더 만들면 초과한다.** (정적 사이트는 인스턴스 시간을 쓰지 않으므로 무관하다.)
- `DATABASE_URL`은 **Session pooler(포트 5432)** 문자열만 쓴다.
  direct 호스트는 IPv6 전용이라 Render에서 못 붙고, transaction pooler(6543)는
  Prisma prepared statement가 깨진다.

## 폐기된 규칙

> "슬립 방지 cron은 다시 걸지 말 것."

Neon 시절에 세운 규칙이다. Supabase로 옮긴 뒤로는 유효하지 않다.
크론은 위 조건(`/item/list`, 10분, 시간대 제한)을 지키는 한 문제없다.
