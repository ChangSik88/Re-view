# ADR 0002 — 데모 남용 방지를 IP 기반에서 방문자 ID 기반으로 바꾼 이유

- 상태: 채택됨
- 날짜: 2026-09-16
- 관련 문서: [홍보 웹페이지 설계 spec](../50-specs/2026-09-09-promo-web-page-design.md), [구현 계획](../superpowers/plans/2026-09-09-promo-web-page.md), PR #46

## 배경

최초 설계(spec 3.4)는 IP당 2회/일 + 전역 200회/일로 남용을 막았다. IP 추출은
`X-Forwarded-For`의 최좌측 값을 쓰는데, 두 가지 문제가 이미 알려져 있었다:

1. 헤더는 클라이언트가 위조할 수 있다 — spec도 이 사실을 인지하고 "확인 전까지는
   전역 상한이 유일한 방어선"으로 명시했다.
2. **공유 네트워크(학교·카페·회사 와이파이, 통신사 CGNAT) 뒤의 방문자는 전부 같은
   공인 IP로 보인다.** "IP당 2회"가 실제로는 "그 네트워크 전체 2회"가 되어, 정당한
   사용자가 남의 시도 때문에 차단된다. 스펙에는 이 케이스가 명시돼 있지 않았다.

## 검토했다가 버린 대안: 쿠키

방문자 식별을 쿠키로 옮기는 안을 검토했다. WEB(정적 호스팅)과 BE(Render)가
서로 다른 도메인이라, BE가 심는 쿠키는 브라우저 기준 **서드파티 쿠키**다.

- Safari(아이폰 포함)는 서드파티 쿠키를 기본으로 전면 차단한다. 예외 신청도 없다.
- 차단은 **에러 없이 조용히** 일어난다 — 다음 요청에 쿠키가 안 붙어 서버는 매번
  새 방문자로 본다. 즉 사파리 사용자는 사실상 무제한이 되어 버린다. spec 3장이
  "출근길 모바일"을 주 시나리오로 잡았는데 국내 iOS 점유율을 감안하면 드문 예외가
  아니라 흔한 실패 경로가 된다.
- 쓰려면 `SameSite=None; Secure` + `credentials: "include"` +
  `Access-Control-Allow-Credentials: true`까지 다 맞춰야 한다. 지금
  `allow_credentials=False`(spec 3.5, "데모는 쿠키·인증을 쓰지 않는다")를 뒤집는
  대가치고, 위 차단 문제를 해결해 주지도 않는다.

## 결정

**클라이언트가 `localStorage`에 익명 ID를 직접 만들어 커스텀 헤더로 보낸다.**
쿠키가 아니다 — 브라우저가 자동으로 붙이는 게 아니라 우리 JS가 직접 헤더에 넣는다.
"다른 사이트가 몰래 심는 추적 장치"로 분류될 근거가 없어 브라우저가 막을 이유가
없다. CORS 설정도 그대로 둔다(`allow_credentials=False` 유지, `allow_headers`가
이미 `["*"]`라 커스텀 헤더도 추가 설정 없이 통과한다).

- 헤더 이름: `X-Demo-Visitor-Id`
- 생성: `crypto.randomUUID()`, `localStorage`에 저장(키: `demoVisitorId`)
- 서버는 이 값을 그대로 카운터 키로 쓴다. IP는 헤더가 없을 때(JS 비활성, 직접
  API 호출)의 **폴백**으로만 남긴다.

**우회 난이도는 쿠키·IP와 동일하다** — 시크릿 창, `localStorage.clear()`, 다른
브라우저로 전부 새 신분이 된다. 이건 로그인 없는 익명 데모에서 근본적으로 피할
수 없는 트레이드오프로 받아들인다(spec의 IP 위조 수용과 같은 성격). 대신
**공유 네트워크 오탐은 완전히 사라진다** — 그게 IP 방식의 진짜 문제였다.

## 부수 결정: 한도 조정

- 방문자당 2회/일 → **5회/일**. 기기 단위 식별로 바뀌어 오탐 여지가 줄었고,
  체험 허들을 낮추는 쪽으로 조정.
- 전역 200회/일 → **300회/일**. Gemini 계정 자체의 일일 상한이 300이라는 것이
 이미 알려져 있어, 무한정 남용은 애초에 모델 쪽 캡으로 막힌다.
  - **주의**: `analyze_dream_chat`은 로그인 사용자의 실제 채팅 해몽과
    **같은 API 키·같은 일일 쿼터**를 쓴다. 데모가 300을 다 쓰면 그날 진짜
    사용자에게 남는 여유가 없다. 문제가 되면 로그인 사용자와 데모 트래픽을
    쿼터 상에서 분리하는 것으로 대응한다(예: 별도 API 키, 또는 데모 전용 하한).
    지금 단계에서는 하지 않는다 — 사용자 판단.

## 결과

- `X-Forwarded-For` 로그가 **모든 요청이 아니라 IP 폴백 경로에서만** 찍힌다.
  정상 브라우저 트래픽은 이 분기를 안 타므로, "방문자 IP를 저장하지 않는다"
  (spec 3.7)는 원칙과의 긴장이 크게 줄었다 — 완전히 사라지진 않는다(폴백이
  실제로 발동하면 그 IP는 여전히 로그에 남는다).
- `reason: "ip"`였던 429 응답 필드값을 `reason: "visitor"`로 바꾼다. 더 이상
  IP 기반이 아니므로 이름을 정확하게 맞춘다. `WEB/app.js`의 분기는 `"global"`만
  특별 취급하고 나머지는 전부 같은 문구를 쓰므로 이 변경에 영향받지 않는다.
